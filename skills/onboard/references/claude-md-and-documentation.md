## Phase 3: CLAUDE.md

Two different files are in play here; keep them straight.

`.launch-control-onboard/prospective-claude.md` — **Phase 2d already wrote it.** Read it; do
not rebuild the block here, and never rewrite it after reading the on-disk `CLAUDE.md` —
the comparison below is only meaningful because the prospective content was fixed before
anything read the current file. If the file is absent, Phase 2d did not complete: go back
and finish it rather than reconstructing the block at this point.

`CLAUDE.md` — **this phase writes it**, in whichever of scenarios A, B, and C applies,
using the exact content read above. Do not rediscover or independently reconstruct
conventions after Launch has been rendered.

The completion renderer independently extracts the final on-disk generated block and requires
a byte-for-byte match against that file before it can accept `CREATED`, `MERGED`, or
`PRESERVED`; a structurally plausible stale block cannot pass as preserved.

That byte comparison proves the two surfaces agree; it can never show **which** one was made
to agree. Rewriting the prospective block to match an already-written `CLAUDE.md` produces a
byte-identical pair, indistinguishable from honest regeneration, so the ordering rule above is
enforced by provenance rather than by content: the completion guard records every write to
`CLAUDE.md` and to `.launch-control-onboard/prospective-claude.md` in
`.launch-control-onboard/write-order.guard.txt`, and the renderer refuses any run whose last
prospective write follows its last `CLAUDE.md` write. A `PRESERVED` run that never writes
`CLAUDE.md` has nothing to invert and passes. The report states what was attested on its
`claude-md-provenance:` line; when no hook ran to record the order, that line says so instead
of implying the comparison alone proved freshness.
Byte-compare only the existing onboard generated block with that prospective block:
`MERGED` when the block differs and `PRESERVED` when it is byte-identical. Never infer
freshness from the snapshot date, partial inspection, or content outside the block.
That rule governs CLASSIFICATION, and only classification. It does not exempt the prose outside
the block from the Phase 0 freshness comparison, which asks the different question of whether
that prose contradicts a fact the generated block asserts; a run may classify this file
`PRESERVED` and still have been required to block in Phase 0 over the paragraph above the block.
Classifying `PRESERVED` means the block was compared, never that the comparison was
unnecessary: the renderer requires the prospective file on the `PRESERVED` path exactly as
it does on `CREATED` and `MERGED`, so an idempotent re-run that changes no file on disk
still depends on Phase 2d having written it.

### The generated block boundary

The generated block carries NO comment markers and no other machine scaffolding: a reader
of the file must see only markdown. The block is located by its stable heading instead.
It begins at the line `## Generated Quick Reference` (exactly, as its own line) and runs to
the next top-level `# ` heading or to the end of the file, whichever comes first. Because the
boundary is the heading, the body inside the block uses only `##` and deeper headings, never a
top-level `# ` heading. The block is always the tail of the file unless user content below it
starts with its own top-level heading. This is the same boundary the completion renderer
extracts, the one `offboard` strips, and the one a later run replaces, so the first
run and every later run use the same replacement boundary. Never create a generated section
that lacks the heading. Never emit `<!-- ... -->` comments, "generated by" banners, or
"re-run to update" notes into the file, and never use the em dash character in generated
text (use a comma, colon, or parentheses).

Three scenarios, handle the one that applies:

### A. No CLAUDE.md exists

Create the file as exactly the generated block: line 1 is `## Generated Quick Reference`,
followed by the entire generated body (project name and stack summary first).

```markdown
## Generated Quick Reference

<generated body>
```

The generated body contains:

1. Project name + detected stack summary
2. Build/test/lint/dev commands (prefer CI-derived, then README, then detected)
3. Monorepo commands (if applicable)
4. Code style conventions (from linter/formatter config)
5. Git workflow (base branch, branch naming from git history patterns)
6. Index of generated skills, agents, commands
7. The complete installed CRISPY chain and its review checkpoints
8. MCP integration notes

For a repository whose CI declares lint, typecheck, and test gates, use these exact
generated headings inside the generated block:

- `### Local validation commands` — list only the independently derived local lint,
  typecheck, and test commands, in the renderer's derived spelling: pytest coverage
  flags stripped, non-gating (`|| true`) CI commands excluded.
- `### CI-owned checks` — list build and end-to-end commands that CI owns; never describe
  them as local `/validate` gates.

Under a repo-root `uv.lock` or `poetry.lock`, that derived spelling is the project-runner
form (`uv run pytest`) or the venv-local form (`./.venv/bin/pytest`), never the bare tool
name. Use the identical string in the generated block, the `Bash(<command>)` permission,
`/validate`, and `testing-patterns`, so no generated surface disagrees about how the local
gate is actually run.

The `/validate` table row must explicitly say it runs the local gate set. Never preserve
or generate `4 CI gates`, include build in the local command block, or say `/validate`
runs every CI gate locally. A rerun replaces the entire owned generated block and must migrate
older generated wording even when all user-authored content outside the block is preserved.

Derive commit and PR conventions from repository evidence. The commit-subject default is
`up to 150 characters`; override it only when an explicit repository-controlled source
states a different numeric maximum. Observed commit-subject lengths, including a history
where every subject happens to be shorter than 72 characters, are not evidence of a
72-character limit. The PR-title default remains `under 72 characters` and likewise changes
only when an explicit repository-controlled source states another maximum. If no explicit
rule exists, label these values as defaults. Apply the resolved commit rule consistently to
the generated `CLAUDE.md`, `dispatcher` agent, `/commit` command,
`feature-development` skill, and Launch. Pass the exact prospective `CLAUDE.md` section
into Launch so the generated surfaces cannot disagree about title length, commit format,
or approval requirements.

For every scenario, describe branch rules as conventions unless the final parsed
`.claude/settings.json` actually contains the matching enforcement hook. Verify live
tool availability before adding machine-specific dependency warnings to `CLAUDE.md`.

### B. CLAUDE.md exists, no generated section

Append the generated block after the existing content, separated by one blank line.
Content above the heading is preserved untouched:

```markdown
## Generated Quick Reference

### Commands

...

### Skills & Agents

...
```

### C. CLAUDE.md exists with previous generated section

Replace ONLY the generated block: from the `## Generated Quick Reference` line to the next
top-level `# ` heading or end of file. Everything outside the block is untouched. If the
existing file carries a legacy `<!-- BEGIN GENERATED SECTION -- onboard -->` ...
`<!-- END GENERATED SECTION -- onboard -->` comment block from an older onboard version,
replace that whole marker-delimited span (both marker lines included) with the new block
so no comment scaffolding remains; the renderer refuses a `CLAUDE.md` that still carries
the legacy markers.

## Phase 4: Documentation Bootstrap

Runs for every normal onboarding. A greenfield project needs no prerequisite; Phase 3
creates its first `CLAUDE.md` before this phase runs.

Check for existing artifacts:

- If `artifacts/architecture.md` AND `artifacts/infrastructure.md` already exist, label
  them as existing snapshots and `PRESERVED`; do not claim they are current forever.
  Surface `docs-update` as the explicit refresh path when repository structure or
  commands have changed.
- If some exist but not all, only generate missing ones.

Preservation is not a freshness pass. Phase 0 already compared every material fact used by the
generated workspace — commands, layout, lifecycle, and security boundaries — against each
preserved document and recorded a verdict per document in the discovery report, and the
checkpoint refused to unblock the first write over any `contradicts` line. Do not infer
staleness from a date or changed HEAD alone. This phase is the backstop for a contradiction
that only becomes visible here — one surfaced while `docs-create` generates a missing
document, or in a degraded session where no hook ran. It carries the same remedy: if live
evidence contradicts or materially extends a preserved snapshot, do not overwrite the
user-owned document and do not render a successful report with `Next: none`; emit the blocked
protocol naming every stale document under `Failed (<N>)` — never only the first — and direct
the user to run `docs-update`. Only evidence-consistent preserved snapshots may pass Phase 5.

When generating, invoke the `docs-create` skill. Reuse Phase 0 discovery context — no redundant scanning. Pass the specific missing document(s) as arguments. Do not author either document directly from `/onboard`: the bootstrap skill's own `PreToolUse` hook records session-scoped proof for each document it writes, and the completion renderer rejects a newly created architecture or infrastructure document without that proof.

Pass these non-negotiable source facts into that invocation and verify them in the final
documents before Phase 5:

1. `/onboard` creates only the paths in the active onboarding manifest. The CRISPY
   workflow skills create `workbench/<TICKET>/<stage>/` later; `workbench/` is not part
   of the onboarding-generated target layout.
2. Classify every MCP from its actual config shape. URL entries such as GitHub and
   Atlassian are authenticated remote integrations. Command/args entries such as
   shadcn and chrome-devtools are local stdio servers and must not be described as
   OAuth integrations or as requiring `/mcp` authentication.
3. The completion guard is declared in this installed skill's frontmatter and is active
   only for the skill lifecycle. It is not registered in user config, installed config,
   or generated project settings. The `--enable-hooks` overlay is separate.
4. Keep portability claims consistent with detected runtime requirements. Do not claim
   that a tool needs no runtime installation when its documented checks invoke tools
   such as `node`, `jq`, or `rg`; say that it needs no project dependency installation
   or build step instead.
5. On Launch Control itself, document the active/baseline/tasks/report-proof/disarmed state
   lifecycle, successful cleanup boundary, same-session re-arm on a later `/onboard`,
   and the fact that unrelated same-session tool use remains unhooked after completion.
6. On Launch Control itself, document protection for arbitrary root and nested `.env*`
   variants, and that the safe examples (`.env.example` and friends) are blocked through
   native Read/Glob/Grep as well, because the broad denies match their names too.

Fail the documentation audit if architecture or infrastructure output collapses those
categories, attributes `workbench/` creation to `/onboard`, or makes a blanket OAuth
claim about a mixed MCP catalog. Also fail if either document says the completion guard
is registered in `~/.claude` config or project settings. These are per-document gates:
both `artifacts/architecture.md` and `artifacts/infrastructure.md` must independently
name GitHub/Atlassian as authenticated remote MCPs, shadcn/chrome-devtools as local
stdio servers, and later CRISPY skills as the creator of `workbench/`. On Launch Control
dogfood runs, the bundled renderer verifies these facts directly and refuses to render
success when either document omits one.

For every project, require architecture to include Overview, Technology Decisions,
System Architecture, a Mermaid component/data-flow diagram, Component Deep Dives, and
Data Model (with an explicit not-applicable explanation when there is no persistent
model). Require infrastructure to include Configuration, Security, and Runbook. A newly
created document says `Generated snapshot`, never `Existing snapshot`. Before Phase 5,
verify the generated `CLAUDE.md` section links to both `artifacts/architecture.md` and
`artifacts/infrastructure.md`.

### 4b. Finalize opt-in hooks

This is the final project-content write phase and runs only with `--enable-hooks`.
Before installing hooks, finish every generated guidance update, including wording in
`CLAUDE.md` that accurately states branch protection is enabled. Then create the missing
`.claude/hooks/skill-eval.sh` and merge the hook entries into settings as planned in
Phase 1c. Parse the final settings and verify the hook script is executable.

After hook registration, perform no further Edit or Write tool calls in the project.
Phase 5 may run read-only audits and declared Bash validation commands, create its
temporary ledger under `.launch-control-onboard/`, and render the report. This order prevents the
new PreToolUse hook from self-blocking the onboarding run on the detected base branch.
