# Testing Patterns

## When to Use
- Writing new tests or test files
- Debugging failing tests
- Creating mocks or fixtures
- Following TDD (Test-Driven Development)

## Test Structure (AAA Pattern)
```
// Arrange - set up test data
// Act - call the function under test
// Assert - verify the result
```

## Factory Functions
Create reusable test data builders with sensible defaults and override support.

## Mocking Strategy
- Mock at module boundaries only (external APIs, databases, file system)
- Never mock internal modules

## Running Tests
```bash

{{DETECTED_TEST_CMD}} {{DETECTED_TEST_FILE_PATTERN}}

{{DETECTED_TEST_WATCH_CMD}}

{{DETECTED_TEST_COVERAGE_CMD}}
```

- Testing implementation details instead of behavior
- Mocking internal modules
- Large test files (split by behavior)
- Skipped tests without TODO comments

allowed-tools: Read, Grep, Glob, Bash(git status:*), Bash(git diff:*)

# Code Review

## Process
1. Run `git status --short` to inventory committed, staged, unstaged, and untracked work
2. Run `git diff origin/{{DETECTED_BASE_BRANCH}}...HEAD` for committed branch changes
3. Run `git diff HEAD` for staged and unstaged tracked changes; read every untracked file listed by status
4. Apply checklist below

## Checklist

### Quality
- [ ] No untyped variables (no `any` in TS, proper types elsewhere)
- [ ] No unused imports or variables
- [ ] Functions focused and small
- [ ] Consistent naming conventions
- [ ] Proper error handling

### Security
- [ ] No hardcoded secrets or API keys
- [ ] User input validated and sanitized
- [ ] No injection vulnerabilities
- [ ] Sensitive data not logged

### Performance
- [ ] No unnecessary computation in hot paths
- [ ] Efficient data structures
- [ ] No memory leaks (cleanup handlers, listeners)
- [ ] Lazy loading for heavy modules

### Testing
- [ ] Unit tests for new business logic
- [ ] Edge cases covered
- [ ] No skipped tests without explanation

## Feedback Structure
1. **Critical** - Must fix (bugs, security)
2. **Suggestions** - Would improve, not blocking
3. **Questions** - Need clarification
4. **Praise** - Good patterns to acknowledge
```

### systematic-debugging

```markdown
---
name: systematic-debugging
description: >
  Use when investigating bugs, errors, or unexpected behavior.
  Four-phase methodology: reproduce, locate, fix, verify.
allowed-tools: Read, Grep, Glob, Bash(rg:*), Bash(git log:*), Bash(git blame:*), Bash({{DETECTED_LINT_CMD}}), Bash({{DETECTED_TYPECHECK_CMD}}), Bash({{DETECTED_TEST_CMD}})
---

# Systematic Debugging

## Phase 1: Reproduce
- Get exact steps to reproduce
- Is it consistent or intermittent?
- Create minimal reproduction or test case

## Phase 2: Locate
```bash
# Search for error text
rg "error message" -l

# Check recent changes to suspect file
git log --oneline -10 -- path/to/file

# Find when bug was introduced
git bisect start
git bisect bad HEAD
git bisect good <known-good>
```

## Phase 3: Fix
- Understand root cause (not just symptoms)
- Make minimal, focused change
- Add regression test that fails before fix, passes after

## Phase 4: Verify
```bash
{{DETECTED_TEST_CMD}}
{{DETECTED_LINT_CMD}}
{{DETECTED_TYPECHECK_CMD}}
```
- Retest original reproduction steps
- Check for side effects in related functionality

## Common Bug Categories
| Category | Symptoms | Usual Cause |
|----------|----------|-------------|
| Race condition | Intermittent | Async ops, shared state |
| Null reference | "undefined" errors | Missing checks, async timing |
| Type mismatch | Wrong output | Bad assertions, implicit casts |
| State bug | UI not updating | Stale closures, wrong updates |
| Logic error | Wrong result | Off-by-one, bad conditionals |
```

### /fix

Use this template only when the project **declares** a fix or format command, a package
script, task-runner target, or config-declared command whose own definition already
contains `--fix`, `lint:fix`, `format`, `fmt`, or a formatter binary. Apply the `/fix`
eligibility test in the onboard skill's Phase 2c; it reads declarations, never a linter's
capabilities.

When nothing is declared, `.claude/commands/fix.md` is skipped rather than stubbed:
account for it under `SKIPPED` and never write a no-op command that explains there is
nothing to fix. `{{DETECTED_LINT_FIX_CMD}}` is only ever a declared command; do not fill it
by appending `--fix` to a declared lint command. A project declaring `lint: next lint` and
no fix or format script gets no `/fix`, even though `next lint` accepts `--fix`.
